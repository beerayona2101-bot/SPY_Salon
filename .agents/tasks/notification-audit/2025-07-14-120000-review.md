# Notification system wired end-to-end into SPY Salon Flutter app

The change adds a complete notification pipeline that was previously missing: a monochrome Android
notification icon, five new API methods in `ApiService`, a `NotificationScreen` from scratch, FCM
navigation rewritten to push that screen, and a notification bell with unread badge added to both
dashboard AppBars. Every component follows the existing `AppColors.of(context)` pattern and the
`_requestWithRetry` + `debugPrint` error-handling convention already used throughout the codebase.
Firebase initialization, token lifecycle, permission flow, and all backend business-event triggers
were verified intact and left untouched.

Watch for: (1) **confirmed** — the notification bell badge uses a hardcoded `Color(0xFFE57373)` in
both dashboards, violating the AppColors design requirement; (2) **confirmed** — `getUnreadNotificationCount`
casts the JSON count with `as int`, which throws at runtime if the backend returns the number as a
`double`; (3) **likely** — `handleNotificationNavigation` acquires a `BuildContext` from the
navigator key to show a `SnackBar`, but the context may be stale when the app launches from a
terminated state.

**Verdict**: NEEDS_CHANGES

## High-level view

Both `AndroidManifest.xml` FCM meta-data tags are present and the channel id matches the one
created in `_initLocalNotifications()`. `ic_notification.xml` uses `@android:color/white` on a
standard 24 × 24 viewport — the correct format for the Android notification tray.

`NotificationScreen` colors all go through `AppColors.of(context)`. The unread dot on each tile
uses `primaryColor` (a theme token), not a literal — the hardcoded color issue is isolated to the
badge in the dashboard AppBars, not inside `NotificationScreen` itself.

Both dashboard AppBars add the bell icon and badge as an additive `actions` entry without touching
existing actions. The badge uses `const BoxDecoration(color: Color(0xFFE57373), ...)` in both
files. That literal is not an `AppColors` token and will not adapt to theme changes or dark mode.

The five new `ApiService` methods match the existing `_requestWithRetry` + `debugPrint` pattern.
The one type-safety gap is in `getUnreadNotificationCount`: `(payload['unreadCount'] ?? 0) as int`
throws a `TypeError` if the backend (e.g. through a MongoDB `$sum` aggregation) returns the count
as `0.0`. The `try/catch` silently swallows the error and returns 0, so the badge silently stops
updating without any indication to the user.

`handleNotificationNavigation` pushes `NotificationScreen` for all notification types and prepends
a `SnackBar` for appointment and leave types. It obtains `BuildContext` from
`_navigatorKey?.currentContext` and guards with `navigatorState == null || context == null`, but
a non-null context that belongs to a disposed widget passes that guard and then throws when passed
to `ScaffoldMessenger.of(context)`. The most exposed path is the terminated-state handler, which
fires after a 1 200 ms delay into an app that may have navigated past the root widget.

<summary>Details</summary>

### Unsafe cast in unread count fetch

```dart
return (payload['unreadCount'] ?? 0) as int;   // ← throws TypeError on double
```

`dart:convert` decodes JSON numbers as `int` when there is no decimal point and as `double` when
there is. A MongoDB `$sum` aggregation on an empty collection returns `0` as a `double`. The
`try/catch` handles the exception gracefully by returning 0, but silently — the badge never updates
after any such response, and the dashboard shows a stale zero count with no error logged or shown
to the user. `.toInt()` on a `num` is always safe.

### Hardcoded badge color breaks theme contract

Both dashboard AppBars use `const BoxDecoration(color: Color(0xFFE57373), ...)` for the unread
count badge. `AppColors` exposes an `error` token used throughout the rest of the codebase for
error states. `0xFFE57373` is Material Red 300 and does not appear anywhere else in the project.
In dark mode, or after any brand palette update, this badge will remain a mismatched red. The fix
is a one-line substitution: `color: themeColors.error` in each file's `Positioned` badge container.

### Navigation context safety on cold start

`handleNotificationNavigation` after the fix:

```dart
final navigatorState = _navigatorKey?.currentState;
final context = _navigatorKey?.currentContext;

if (navigatorState == null || context == null) { return; }

final colors = AppColors.of(context);   // ← context may be detached
ScaffoldMessenger.of(context).showSnackBar(...);
navigatorState.push(...);               // ← push is safe regardless
```

The hazard is narrow: if the user navigates past the root widget during the 1 200 ms terminated-state
delay, `context` is detached but non-null. A `context.mounted` guard before the SnackBar call
(not before the push) fully eliminates it. The navigation push itself does not require a mounted
context and is safe as-is.

### Optimistic state not reverted on API failure

`NotificationScreen._onTapNotification` marks the tile as read locally before `markNotificationRead`
returns. If the API call returns `false`, the tile remains visually read while the backend has it
as unread — the discrepancy is resolved only on the next full refresh. The screen has no revert
path. Not tested: this failure mode, badge count accuracy when the server returns non-integer
unread counts, and terminated-state navigation on real hardware.
